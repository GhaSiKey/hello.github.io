# AI 模拟买盘战绩页 · 设计文档

> 状态：设计稿，待评审。遵循「文档先行 → 方案确认 → 开发」工作流。
> 关联：依赖 [worldcup-web.md](worldcup-web.md) 的数据与 commentary.plan。

## 1. 产品定位

用**真实赛果**检验 worldcup 页里 AI 给出的每场娱乐方案——这一波 AI 是
封神还是打脸。本质是一张「AI 投注战绩对账单」。

核心呈现：**总支出 / 总收入 / 总盈亏 / 命中率**，加一条按开赛时间排列的
**战绩时间线**，逐场显示：押了什么、真实比分、本场盈亏、命中标记。

**它不是什么**：不是真实投注、不替任何人下注、不承诺收益。是对 AI 方案的
事后复盘，纯娱乐与自省。

## 2. 现实约束（必须先认清）

- **比赛 2026-06-12 才开赛**。在赛果出来前，本页只有"支出"和"押了什么"
  是已知的；收入/盈亏/比分/命中全部为"待开赛"。
- 因此页面分两种状态：
  - **赛前**：显示总支出（15 场 × 20 = 300 元）、每场押注内容，结果区占位。
  - **赛后**：逐场补入真实比分、自动判定输赢、累计盈亏。
- 数据随赛事推进**增量填充**：哪场踢完了，哪场就有结果，不是一次性全亮。

## 3. 数据来源与判定可行性

### 3.1 赛果来源（已初步验证，含风险）

`getMatchHeadV1` 接口返回 `fullCourtGoal` 字段，赛前为空字符串。
**推断它是赛后填充的全场比分**（字面"全场进球"）。

- ✅ 若赛后被填充为可解析比分（如 `"2:1"`）→ 自动爬取赛果可行。
- ⚠️ **风险**：现在无法确认其赛后格式与填充时效。列为「待验证依赖」。
- **兜底**：若该字段不可用，赛果由人工（赛后让 AI 看比分）填入 `result` 字段，
  判定逻辑不变。无论自动还是手动，赛果都落到统一的 `result` 字段。

### 3.2 输赢判定（结构化是前提）

当前 `commentary.plan.bets[].market` 是中文自由文本（如"让球-1 让胜"），
机器无法解析。**必须把每注结构化**，加机器可读的判定信息：

```jsonc
{
  "market": "让球-1 让胜",      // 展示用，保留
  "type": "hhad",              // 玩法类型(机器判定用)
  "pick": {"goalLine": -1, "side": "h"},  // 选项
  "odds": 2.20, "stake": 12
}
```

判定函数 `judge(type, pick, result)` 拿真实比分 result（如 {h:2,a:1}）
按各玩法规则算中/不中。规则见 §6。

## 4. 数据契约（扩展 worldcup.json，不新建文件）

战绩数据复用并扩展现有 `data/worldcup.json`，避免数据分裂：

**4.1 每场新增 `result` 字段（赛后填）**

```jsonc
"result": {
  "status": "pending",        // pending(未赛) | finished(已赛)
  "half": {"h": 0, "a": 1},   // 半场比分(半全场判定用,可选)
  "full": {"h": 1, "a": 1},   // 全场比分
  "source": "auto",           // auto(接口爬) | manual(人工填)
  "filledAt": "2026-06-12T05:00:00+08:00"
}
```

**4.2 `commentary.plan.bets[]` 每注补结构化判定字段**

在现有 market/odds/stake/potential 基础上加 `type` + `pick`：

```jsonc
{
  "market": "平局", "odds": 2.84, "stake": 10, "potential": 28.40,
  "type": "had", "pick": "d"
}
```

**4.3 判定结果（赛后由判定函数写入每注）**

```jsonc
"hit": true,          // 是否命中
"payout": 28.40       // 该注实际派彩(命中=potential, 不中=0)
```

**4.4 全局战绩汇总（meta 下新增，赛后算）**

口径分离：盈亏/ROI 用「已结算」口径（只算已开赛场次的投入与回款），
全预算单列作「总支出」。否则未结算场的预算会被当亏损，开局必然趋近 -100%。

```jsonc
"betSummary": {
  // 全预算口径（展示"总支出"）
  "totalBudget": 300, "totalMatches": 15, "totalBets": 44,
  // 已结算口径（盈亏/ROI 主显示）
  "settledStake": 40, "settledPayout": 41.68,
  "profitSettled": 1.68, "roiSettled": 0.042,
  "finishedMatches": 2, "hitBets": 2, "settleableBets": 5,
  // 账面浮亏（含未结算场预算，次要信息）
  "profitBudget": -258.32
}
```

- **命中率**用 `hitBets/settleableBets`（可结算注），不用 totalBets——
  无法结算的注(缺半场)不进分母，口径诚实。
- 战绩页「总盈亏」主显示 `profitSettled`（反映 AI 押的这几场准不准），
  `profitBudget` 作次要参考。

## 5. 各玩法 type 与 pick 约定

| type | 玩法 | pick 形如 | 判定依据 |
|------|------|----------|---------|
| `had`  | 胜平负 | `"h"`/`"d"`/`"a"` | 全场比分比大小 |
| `hhad` | 让球胜平负 | `{goalLine:-1, side:"h"}` | 主队进球+goalLine 后比大小 |
| `crs`  | 比分 | `{h:1, a:0}` 或 `"other_h"` | 全场比分精确匹配 |
| `ttg`  | 总进球 | `2`（=2球，`7`=7+） | 主+客进球数 |
| `hafu` | 半全场 | `{half:"d", full:"h"}` | 半场+全场各自胜平负 |

## 6. 判定规则（judge 函数）

```
had:   side=h → full.h>full.a；d → ==；a → full.h<full.a
hhad:  令 H=full.h+goalLine；side=h → H>full.a；d → ==；a → H<full.a
crs:   pick.h==full.h && pick.a==full.a（"other_*"按胜平负归类后比分不在所列项）
ttg:   pick==min(full.h+full.a, 7)
hafu:  half 判定用 result.half，full 判定用 result.full，两段都对才中
```

> hhad 让球玩法本是串关（前面数据 single=0），但本页是"模拟单买复盘"，
> 按单关结果判定即可，并在页面注明"模拟为单关口径，与真实串关规则有别"。

## 8. 文件结构

```
simbet.html                 # 战绩页骨架
css/simbet.css              # 样式(复用 worldcup 变量)
js/simbet/
├── judge.js                # 判定函数(纯逻辑,可单测) —— 核心
├── render.js               # 汇总卡 + 时间线渲染
└── app.js                  # 入口,读 data/worldcup.json
tools/
├── add_bet_meta.py         # 给 plan.bets 补 type/pick 结构化字段(一次性/可重跑)
└── settle_results.py       # 赛后:爬/填赛果 + 判定 + 算 betSummary,写回 json
```

> judge.js 与 settle_results.py 的判定逻辑必须一致（同一套规则两端实现）。
> 抽到共享的规则说明(§6)，改动需同步——与 worldcup 模块同样的约束。

## 9. 工作流程

**赛前（现在可做）**：
1. `add_bet_meta.py`：给现有 15 场的 plan.bets 补 type/pick（结构化）。
   —— 这步要 AI 介入，因为要把中文 market 映射成 type/pick，需理解语义。
2. 建页面，赛前展示支出 300 + 各场押注，结果区"待开赛"。

**赛后（每有比赛结束）**：
3. `settle_results.py <mid> <主> <客> [半主 半客]`：填真实比分 → judge 每注
   → 重算 betSummary，写回。**不联网、只动指定场**（与 build 全量覆盖隔离）。
4. 刷新页面看最新战绩。

**已实现的 skill**：
- `/worldcup`（赛前）：爬赔率 + AI 写点评。
- `/settle`（赛后）：WebSearch 搜比分 → 列清单给用户确认 → 调 settle_results.py
  批量结算。比分走搜索而非体彩接口（接口已 403 反爬），半场搜不到则该场
  半全场注标"无法结算"。

**赛果来源经验**：体彩 `fullCourtGoal` 字段因接口 403 未能验证可用；实践改用
WebSearch + 用户确认，更稳。`settle_results.py` 的比分由参数传入，不绑定来源。

**踩坑记录**：曾误用 `build_wc_data.py` 结算，其"抓不到=空场"逻辑在 403 时
把 worldcup.json 清空。已修复：build 脚本抓取场次少于已有时拒绝写入(需
--force)。结算一律用 settle_results.py。

## 10. 已定决策（评审确认）

| # | 问题 | 决策 |
|---|------|------|
| 1 | 结构化谁做 | AI 在对话里把中文 market 映射成 type/pick（需理解语义） |
| 2 | 半全场缺半场比分 | 拿不到半场 → 该注标「无法结算」，不计盈亏，诚实不造假 |

| 5 | 页面命名 | 待定（暂用 simbet.html） |

**第 2 条的具体处理**：`judge` 对半全场注，若 `result.half` 缺失，返回
`hit: null`（区别于 false），页面标「无法结算」，该注 stake 仍计入支出但
不计入命中统计与派彩。这样总盈亏口径诚实——避免把"没法判断"算成"输"。
